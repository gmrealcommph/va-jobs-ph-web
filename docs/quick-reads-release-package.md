## Practical asset and binding preservation

A complete server-attested asset path inventory is still unavailable. Do not replace the asset set with the 84 reconstructed paths. Use the version-upload API with keep_assets=true and an inherited ASSETS binding. This retains the existing set rather than uploading a reconstructed manifest. All unchanged bindings are explicitly inherited by name with bindings_inherit=strict; only the four generation settings are explicit replacements. No secrets are extracted. Preserve the asset serving options serve_directly=true, raw_run_worker_first=false, base_path=/.

Cloudflare documents keep_assets as retention from a previous uploaded version, and strict binding inheritance resolves against the latest uploaded version, which may differ from active. Therefore require a short operator change freeze and exact active/latest equality before starting. Stage versions without shifting traffic, inspect returned resources, then activate only if all unrelated bindings/runtime settings and assets options agree. Never use a speculative settings PATCH or plain npm run deploy.

Residual risk: retention has a documented contract but this task cannot prove the hidden asset manifest digest or test retention without a version write. The API has no established atomic lock against another uploader here. A freeze plus before/after version checks bounds this race; unexplained drift means stop. Post-upload checks happen while old traffic still serves. If an immutable asset identity is not exposed, accept documented retention lineage plus the 84-path sweep as the bounded assurance level; do not claim full enumeration. Reject missing ASSETS/options or unexpected binding/runtime differences before activation.
