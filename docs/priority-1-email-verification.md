## Behavior and protections

- `/auth/resend` accepts same-origin POST only. Signed-in requests use the Auth account address; signed-out members can enter their registered email. All allowed and throttled attempts get the same generic redirect. Missing storage, missing Cloudflare IP or insufficient/unavailable quota prevents sending.
- Durable resend reservations: 60 seconds between attempts for an address, three attempts per rolling 24h per address, ten per IP/hour, thirty across the app/hour and twenty across the app/rolling 24h. Failed/unknown provider attempts consume a reservation. Postgres advisory locking serializes concurrent workers; no isolate-local limiter is trusted. Address and IP hashes, rather than raw addresses/IPs, are stored for the limiter. Old reservations are purged lazily after two days on subsequent attempts.
- Resends call Supabase's existing signup-confirmation endpoint; no privileged link generation or second welcome email is introduced. Supabase's own rate limits remain active. The API uses `redirect_to` in the URL, matching the official Auth client transport, and preserves `/apply/:id` through confirmation.
- Scheduled reminders are disabled unless `EMAIL_VERIFICATION_REMINDERS_ENABLED=true` and an explicit `EMAIL_VERIFICATION_START_AT` timestamp is set. They contain a link to the resend page; they do not generate an expiring verification token or invalidate a still-working original confirmation email.
- At most one reminder per member per 24h/72h stage, enforced by a unique constraint. The 24h stage applies from 24h to 72h; after 72h only the 72h stage is eligible, avoiding both stages arriving at once after downtime. At least 24h separates new reminders for one member. Processing is best effort from 24h through seven days after signup, within the configured cohort; a backlog can delay or skip a stage.
- Ten new reminder deliveries maximum per UTC day. Resends and reminders require at least twenty remaining emails in both capped Resend windows and fresh available quota monitoring. This reduces load but cannot reserve shared capacity against other apps or concurrent Auth/welcome sends. Existing quota cache can lag by five minutes.
- Before every reminder attempt, Auth is read again; confirmed, deleted, anonymous, banned or changed-address accounts are skipped. The address is frozen in the claim. Account deletion cascades reminder records. Provider suppression remains authoritative; this PR does not alter the existing digest webhook or introduce an independent suppression registry.
- A durable claim precedes provider access. Retries reuse the same reminder UUID idempotency key and message. A 16-minute lease is longer than all request deadlines. Four attempts maximum and a 23-hour retry horizon prevent replay after Resend's 24-hour idempotency window. Pending ambiguous outcomes then require review. Sent timestamps mean provider acceptance, not inbox delivery. Do not manually reset or replay a review row without checking provider logs.
- Private-schema tables have RLS and no member table grants. Sender RPCs are executable only by `service_role`. Public wrappers are security invoker; privileged implementations have an empty search path and explicit revocations. Admin tracking exposes current confirmation timestamps, 24h/72h acceptance timestamps, current counts, and the latest 100 members to approved admins only. Access expiry clears this data in the browser.
- Existing Telegram paths, welcome orchestration, payments/entitlement logic, Quick Read code/configuration, email preferences and existing sending schedules are untouched. Confirmation callbacks now process links even with an existing session and immediately remove bearer tokens from browser history.

## Production activation checklist — requires separate explicit approval

1. Review the draft PR, migration and test evidence. Confirm a rollback owner. Do not merge or deploy under the general implementation approval.
2. Confirm current Auth email confirmation is enabled, custom SMTP is healthy, and the current confirmation template uses the provided confirmation URL. Confirm the Auth redirect allowlist permits `https://veeays.com/auth/callback` with its allowlisted application return query. Inspect existing Auth email caps, token expiry and any CAPTCHA requirements; the reported 100/hour Auth cap has not been independently verified by this implementation. Do not change SMTP, template, CAPTCHA, confirmation, or redirect settings without approval.
3. Confirm the existing welcome flow still delivers once at its intended point. Do not replace it with reminder sends. Check recent bounced/suppressed/complained mail in Resend; confirm provider suppression behavior for the intended reminder cohort before enabling. Resolve unexpected bounce rates first.
4. Exercise an isolated staging copy and controlled mailbox: signup, initial confirmation, unconfirmed password login, expired link, resend cooldown, verification with an existing session, and confirmation in a different tab. Test an anonymous Apply Now through signup → verification → selected stored employer destination, plus an existing verified member. Test refresh-cookie rotation. Confirm payment entitlements, welcome email, Telegram registration/payment alerts, Quick Reads and email schedules still work in their authorized test environment.
5. Apply only `supabase/migrations/20261014134315_priority_1_email_verification.sql` to the approved target. It requires existing `auth.users`, `service_role`, and `veeays_admin.has_access()`. This repository's historical migrations are not a complete production rebuild; do not blindly push/replay unrelated migrations. Run hosted security/performance advisors afterward and confirm anon/member denial plus approved admin access. Keep the private schema outside the Data API's exposed schemas.
6. Confirm Worker secrets `SUPABASE_SERVICE_ROLE_KEY`, `RESEND_API_KEY`, and `RESEND_USAGE_KEY` exist server-side. Confirm usage access returns fresh daily/monthly limits. Confirm `hello@veeays.com` is an approved transactional sender on the verified domain. Do not print secrets or expose them in browser assets.
7. Deploy approved code with reminders still disabled. Verify resend works with a controlled mailbox and that admin status loads. No new cron registration is required. Keep existing production flags, Telegram destinations, payments, schedules and Quick Read settings intact.
8. Approve the cohort explicitly. Set `EMAIL_VERIFICATION_START_AT` to the approved registration cutoff (prefer activation time to avoid unsolicited backlog; a recent existing cohort requires deliberate review). Enable `EMAIL_VERIFICATION_REMINDERS_ENABLED=true` only after that approval. Missing/invalid cutoff blocks work. Check fresh Resend headroom immediately before activation.
9. Observe controlled 24h/72h reminder deliveries and admin receipt states. Check Resend for actual delivery, suppression and bounce outcomes. Confirm no reminder after verification, one receipt per stage, no duplicate welcome, and no app redirect for unverified users. Monitor the 100/day and 3,000/month shared limits; no plan upgrade is included.
10. Roll back reminders by disabling `EMAIL_VERIFICATION_REMINDERS_ENABLED`; preserve receipt history and cohort cutoff. Do not truncate the outbox or reset sent/review records. To roll back the application gate/resend UI, redeploy the previously approved Worker version. The additive private tables/functions may remain inert. Any database removal or production rollback needs explicit approval.
